# 设计说明

## 为什么把两类训练放在一起

TOB 的重点是组织协作、责任与试点推进；TOC 的重点是个体需求、服务匹配和自主决策。两类训练共用对话界面和会话生命周期，但分别维护场景、角色关系和复盘维度，避免套用同一销售脚本。

## 数据流

浏览器选择场景和产品 → 服务端校验 ID → 创建隔离会话 → 规则引擎或兼容模型接口返回回复 → 结束后提取用户原话 → 输出覆盖提示 → 浏览器按需下载。

服务端选定产品后保存独立快照。真实模型上下文只包含这一产品、当前场景及当前会话，不引用其他产品资料。角色互换通过重新开始实现，旧历史不进入新请求。模型失败时不追加本轮消息，可在页面重试。

## 技术取舍

使用 Python 标准库与原生前端，降低演示环境依赖。HTTP 服务只暴露三个静态文件和三个操作接口，不把源码目录当作静态根目录。会话使用随机标识，存储于内存，限制轮数、数量和有效期。Host/Origin 检查限制异源访问，但不是公网身份验证方案。

模型与界面分离，密钥只在服务端。默认模拟模式让观看者不需要购买模型服务；界面明确区分模拟回复和真实模型。复盘采用可解释的关键词覆盖，不输出缺少依据的分数。

## 数据公开策略

采用“独立新建公开工程 + 合成业务资料”的方式，而不是复制业务库后批量替换名称。价格、机构、人物、场景和通用评价维度均为演示新写。公开工程没有原数据映射表，也不提供恢复历史资料的功能。

扫描器对文件类型使用允许列表，并检测部分敏感文本模式。它不扫描 Git 历史，也不能识别所有合同条款或隐含商业信息；新增业务文件仍需人工确认来源。发布包不含 Git 元数据、虚拟环境及缓存。

## 后续可扩展

可增加基于证据片段的结构化模型评分、独立产品事实校验器、可取消的流式对话、语音与长期练习记录。只有功能完成并验证后，才应写入已实现能力。
